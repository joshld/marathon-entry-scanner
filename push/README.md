# Browser notifications (no email required)

Race Entry Radar offers two complementary notification modes:

1. **In-dashboard bell — enabled automatically.** Displays recent, source-backed race updates using the browser's own local storage for the read/unread state. Works on GitHub Pages with no account, push server, extra permissions or cost.
2. **Background browser push — optional and currently disabled.** When enabled, the visitor chooses `Enable browser notifications` and grants their browser permission. GitHub Actions can then send matched updates even after they leave the website. It requires a secure push-subscription store; do not expose push subscription endpoints in a public repository.

## On-site bell

The bell in the heading lists newly added races, verified newly open entries and opening dates within seven days. It respects the dashboard's **Locations** and **Distances** selections. `Mark all read` and clicking an alert save the read state to browser local storage. Each browser/device has its own read state; clearing site data resets it. If you see no changes, broaden the geographic/distance filters. The initial list includes recent confirmed openings even before the event history has accumulated transitions; tentative `possible_open` matches never count as confirmed.

The published scanner's non-personal `data/alert-events.json` accumulates recent trusted events for 90 days. The website also derives current entries-open and opening-soon items from recently verified race records.

## Enabling background push once (optional)

This works without a Brevo account, email sender, or Cloudflare Turnstile. A free Cloudflare Worker and KV namespace store device subscriptions (not emails); a GitHub Actions job sends Web Push via Python `pywebpush` using a VAPID key pair.

**Do not enable public push subscription or push sending until the service is deployed, configuration is tested, and any necessary privacy disclosure is published.** The dashboard's `site/push-config.json` intentionally ships with empty values.

### Step 1 — create one VAPID key pair

On a computer with Node.js, run `npx web-push generate-vapid-keys`. Save both output strings securely. The public key is safe to put in the website. The private key goes **only** in GitHub Actions Secrets.

Don't regenerate the pair after people subscribe: existing subscriptions are bound to that pair. Python `pywebpush` accepts the raw base64url private string generated by this command.

### Step 2 — create a secure subscription store in Cloudflare

1. Create a free [Cloudflare](https://dash.cloudflare.com/) account.
2. Under Workers & Pages / KV, create a Workers KV namespace, for example `race-entry-radar-push`.
3. Create a Worker and paste/deploy `push/worker.js` (ES module).
4. In the Worker's **Settings → Bindings**, add a Workers KV binding named **`PUSH_KV`** pointing to the namespace.
5. Set the following Worker settings:
   - **Text variable** `ALLOWED_ORIGIN` = `https://joshld.github.io` (do not include `/marathon-entry-scanner/`).
   - **Encrypted secret** `PUSH_ADMIN_TOKEN` = a new long random value. Use `openssl rand -hex 32` locally to generate one. The **same** secret goes in GitHub Actions.
6. Deploy the Worker and visit `https://YOUR-WORKER.workers.dev/health`. It should return `{"ready":true}`. Do not share or embed the admin token in any public file.

The Worker only accepts subscription/unsubscription calls from the configured GitHub Pages origin. It stores device push endpoints and encryption keys privately in Cloudflare KV, validates supported push-service hosts, and has an authenticated admin route for the notification job.

**Operational safeguards:** Restrict traffic/rate limits in Cloudflare before opening to significant public traffic. Device push endpoints are pseudonymous but should be treated as private subscriber information. As presently written, this is a small-scale starter implementation, not a replacement for a mature anti-abuse service. If you stop operating the Worker, notify visitors and clean up the stored subscriptions.

### Step 3 — connect the public site (safe fields only)

Edit `site/push-config.json` on GitHub:

```json
{
  "worker_url": "https://YOUR-WORKER.workers.dev",
  "vapid_public_key": "YOUR_PUBLIC_VAPID_KEY"
}
```

The website now exposes the optional push button beneath the bell, registering the site's `site/push-sw.js` service worker when configured. Visitors may select the dashboard's countries and distances **before** enabling push; those selections become their notification preferences. They can revisit the bell and choose **Update browser notification preferences** after changing filters, or **Disable notifications** to unsubscribe.

**Do not put** `PUSH_ADMIN_TOKEN`, the VAPID private key, or push device subscription endpoints in `site/push-config.json`.

### Step 4 — enable scheduled sending (after testing)

In GitHub repository **Settings → Secrets and variables → Actions**:

| Category | Name | Value |
|---|---|---|
| Secret | `PUSH_ADMIN_TOKEN` | Same secret as Cloudflare Worker |
| Secret | `PUSH_VAPID_PRIVATE` | Your private VAPID key |
| Variable | `PUSH_WORKER_URL` | Cloudflare Worker URL |
| Variable | `BROWSER_PUSH_ENABLED` | `true` **only after testing** |

The daily workflow runs at around 7:17 am Brisbane time and only invokes the push job for **scheduled** runs with `BROWSER_PUSH_ENABLED=true`. Committing code or manually running the scanner doesn't blast notifications. Devices receive at most one digest per scheduled run, and only for new matching event records created **after subscription** and not previously acknowledged. The prototype caps sending at 100 devices per run to avoid accidental overuse; unprocessed devices are retried later.

The site can run indefinitely with the bell enabled and background push disabled. Neither mode sends unsolicited email.

### Step 5 — test

1. Open the GitHub Pages dashboard on desktop Chrome, Edge, Firefox or a compatible Android browser.
2. Choose filters, open the bell, and select **Enable browser notifications**. Grant permission and confirm the control changes to **Update browser notification preferences**.
3. Verify the Cloudflare KV namespace contains a `sub:...` item, but do not publish its content.
4. Test `/admin/subscribers` privately using the Worker admin token and verify that `data/alert-events.json` has a new *verified* event. The scheduled push job sends only new events after subscription, so it may be quiet until a genuine race change.
5. Verify the OS receives a notification with the site closed, that clicking it opens the correct entry page, and that **Disable notifications** removes the KV record.
6. For **iPhone/iPad**, add the website to the Home Screen, then open the installed web app and allow notifications there. Safari web push on iOS requires a Home Screen web app; opening the site as a normal tab isn't enough. Other browser/platform permissions vary.

Note: Current availability can change after an event opens. The source-backed scanner deliberately excludes tentative or ambiguous `possible_open` website keywords from verified opening alerts.

## Source and security

- `site/index.html`: in-dashboard bell, unread state and opt-in UI.
- `site/push-sw.js`: browser push receiver and notification click navigation.
- `site/manifest.webmanifest`: installable web app metadata.
- `site/push-config.json`: only public settings; empty until configured.
- `push/worker.js`: private Cloudflare KV subscriber management.
- `push/send.py`: scheduled, matched, bounded push sender.
- `notifications/events.py`: non-personal source-backed event journal.
- `tests/test_browser_push.py`: privacy and event matching regression tests.

See also [Apple's web push requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) and [Cloudflare KV documentation](https://developers.cloudflare.com/kv/get-started/).
